## 1. 现在的产品究竟是什么

应用已有相当完整的本地 ACP 工作流：显式工作区、多 Agent 配置、创建/恢复会话、多会话并行响应、文本/附件输入、权限决策、工具与计划展示、文件阅读、终端，以及本地恢复与 macOS 壳层。它已经超过简单的聊天界面。

但还不能按“全部 ACP 能力实现”或“完整 Agent 平台”介绍。当前是本地 stdio Rust runtime；远程 ACP、fork、MCP-over-ACP 和若干实验协议不能生产执行。Token usage 与实时 session-info 通知还存在生产投影缺口。已有 UI、Fake 测试和静态能力说明不能代替端到端实现。

最值得保护的资产是：**会话与项目身份清楚、同时工作的会话互不干扰、长会话能恢复、执行过程可阅读、异常后有恢复路径。** 对这些能力的判断有明确源码依据；用户是否愿意持续选择本应用，还要用真实任务检验。

主要用户闭环及当前评估：

| 用户步骤 | 当前能力 | 下一步应改善什么 | 不应追加什么 |
|---|---|---|---|
| 1. 准备 Agent | 本地发现、手动配置、认证 | 分清“检测到候选”“可启动”“已认证”“成功会话” | 大型安装商店、多平台安装矩阵 |
| 2. 选择项目并开始 | 工作区、新会话、cwd 补全、模板 | 默认当前项目和常用 Agent；高级 recipe 按需展开 | 强制用户先理解 MCP/provider/模板版本 |
| 3. 执行与干预 | 流式、停止、队列、Guide、权限 | 让等待原因、停止结果、待授权动作清楚 | 新建独立 Inbox/调度器来包裹普通会话 |
| 4. 阅读结果 | Markdown、工具详情、diff、文件预览、本地终端 | 突出结果和相关文件，过程按需展开 | 完整文件编辑器、Git 提交/PR 平台 |
| 5. 回来继续 | 本地索引、显式 Resume、精确版本缓存、崩溃恢复 | 区分本地切换与外部恢复；失败后能继续操作 | 启动时再次扫描一切会话 |

上述是源码流程评估，本轮未录制操作、启动 Agent 或做新的截图审计。

## 3. 功能组合应如何调整

| 功能组 | 判断 | 推荐动作 |
|---|---|---|
| 工作区、创建/恢复、并行会话、取消、草稿 | 主流程价值高，可靠性成本高 | 保留并加强真实 Agent 验证 |
| 聊天、附件、模型选择、slash commands、工具/plan/diff | 直接影响完成任务 | 保留，按实际 Agent 能力显示 |
| 文件链接预览、Markdown/代码阅读、Finder 打开 | 能把对话变成可检查的成果 | 保留只读闭环，停止向完整 IDE 扩张 |
| 工作区创建 worktree | 有用但属于进阶开发流程，Git 回滚成本较高 | 保留高级入口；不和尚未实现的会话 fork 混淆 |
| 手动本地终端 | 减少开发者切换应用，但增加一套生命周期 | 默认收起，维持现有范围；明确切会话会释放终端 |
| ACP filesystem/terminal provider | Agent 协议所需能力与授权边界 | 保留 opt-in 与所有保护，不因 UI 精简删掉 |
| 稳定 MCP、多 Agent、自定义命令 | 当前定位的开放性基础 | 保留；先维护真实常用组合，再增加候选 |
| Session Activity、Permission History | 有排错和决策追溯价值，独立入口重复 | 合并为“活动与诊断”的事件/权限视图 |
| Runtime Inventory、ACP Compatibility、Protocol Coverage | 运行信息有用，静态完成度表已失真 | 以实际 Inventory 为主，能力详情并入；退役静态 Coverage 页面 |
| Inspector、会话设置、输入区模型参数 | 有快捷与完整配置两种需求 | 共用状态，简化详情入口；不必为了“唯一入口”牺牲快捷操作 |
| Session Template | 对反复配置有用，但组合跨目录、MCP、权限、助手与模型 | 先收缩成常用预设；高级字段保留读取兼容，暂不做完整可视化规则编辑器 |
| AI permission reviewer、信任规则 | 可减少人工操作，但可靠语义、延迟与费用需要证据 | 下沉高级，修正规则标识；保持默认人工与未知回人工 |
| AI 标题与逐回合总结 | 本地标题已可用，总结收益未知，增加模型调用 | 维持默认关闭；优先冻结逐回合总结，评估改按需或退役 |
| 音频、二进制内容 | 有通用协议支持，没有独立语音闭环 | 保留现有通用路径，暂不发展语音产品线 |
| Memory、持久 Task/Workflow、远程 ACP、Registry、实验协议 | 当前未交付或已删除，新增成本大 | 暂缓；每项分别通过需求门槛再立项 |

逐项判断与证据见 F01–F78，不建议给整个应用一个伪精确的总分。功能存在、真实兼容、用户价值、维护成本是不同维度。

## 4. 首先处理的具体问题

### 4.1 把产品承诺与执行能力对齐

| 优先事项 | 证据 | 推荐结果 |
|---|---|---|
| 远程 ACP 被描述为可配置即使用 | `protocol_feature_review_dialog.dart:140`；`lib/app.dart:2705` 主动拒绝 | 保存/选择时明确不可用；独立 Coverage 退役前先修文案 |
| fork 被写进产品能力 | `docs/product_capabilities.md:13`；`rust_acp_agent_client.dart:590` unsupported | 从已交付列表移除，UI 隐藏不可执行操作；保留普通 worktree 新建 |
| Extension Request、NES/provider/elicitation 等标“完成” | `protocol_feature_review_dialog.dart:398`；Rust `model.rs:317` 命令面没有对应执行路径 | 不再展示完成度百分比，按实际 typed runtime 能力报告 |
| 用量与实时会话信息有上层消费，却无生产投影 | `runtime.rs:3276`、`:4457`；`chat_controller.dart:7445`、`:7466` | 无数据就显示未知/隐藏；需求明确后补 Rust→FFI→Dart，不补假数据 |
| 文档把 slash commands 也归为不跨 FFI | `docs/conversation_loading_architecture.md:52`；`runtime.rs:4564` | 拆开 commands、目录 SessionInfo、实时通知、usage 四个结论 |
| 信任规则名义上按工具，实际使用调用 ID | `rust_acp_agent_client.dart:1243`；`acp_permission_request.dart:121` | 验证各 Agent 标识语义，稳定 semantic key 未建立前不扩大“一次设置永久适用”的承诺 |

这里不是要求立刻实现所有缺口。对于低价值或范围外的能力，准确地说明不支持，比为了旧文案补一个大子系统更符合当前方向。

### 4.2 精简实际入口

建议主窗口保持：**工作区导航 + 会话内容 + 输入区**。文件预览、本地终端、会话详情为按需打开的辅助区域。

建议菜单结构：

- **Agent**：选择 Agent、认证、管理 Agent。MCP/权限/providers 在管理中的高级配置。
- **会话**：重命名、置顶、归档；“更多”包含复制、在新窗口打开、关闭/删除。
- **会话详情**：项目/Agent/模式/有效目录；完整参数按需展开。
- **活动与诊断**：事件时间线、权限记录、实际运行配置/能力三个视图。

输入区保留模型、推理强度、权限策略等真正影响当前提交的快捷项，并与完整设置共享状态。新建入口在工具栏和项目菜单各保留一个是合理的上下文便利，不需要机械删除所有重复按钮。

“Open Side Session”统一为“在此项目中新建会话”；Guide 明确叫“停止并发送”，实际是 `chat_controller.dart:4448` 取消当前轮后派发队列；“来源”分组只通向详细信息；添加来源回调为空，组件也不会渲染该加号（`workspace_inspector.dart:94`、`:286`）。可改名或合并这个分组，不必为了标题再新增来源系统。

### 4.3 精简代码与维护面

删除候选为未接入生产的 `SessionSidebar`、`WorkspaceHeader`、`StatusBar` 和 `MermaidExamplePage`。全仓 Dart 构造搜索只命中定义与各自测试。删除前仍需检查导出、文档示例和对应测试用途；不要连带删除新壳层正在用的 `WorkspaceSidebar`、`CapabilitiesDialog` 或 Mermaid 渲染器。

保留旧配置的解析兼容和安全迁移，限制 UI 继续创建不可执行配置。隐藏功能、停止扩展、移除源码应分阶段进行；删除 UI 不等于立即删掉其持久数据字段。

## 5. 哪些简化不能做

1. 不把归档、关闭和删除合成一个不可逆动作；它们影响不同的数据与资源。
2. 不把会话注册表、转录缓存、UI 索引当同一种存储。当前容量/保留策略分别生效，UI 索引不受同一策略控制（`docs/sqlite_storage.md:14`）。
3. 不合并用户本地 shell 与 ACP callback terminal 的授权及资源所有权；二者不是同一后端。
4. 不删除目录 canonical 校验、密钥迁移、原子保存、输入预算、权限失效、会话事件隔离与进程回收。
5. 不宣称这里已有完整 Agent 沙箱。工作区约束主要覆盖客户端提供的文件回调及 terminal cwd；本地 shell 或 Agent 自身工具的所有副作用，并没有因此被客户端全面限制。当前 README 也把外部副作用归于 Agent 和工具。
6. 不为“收敛”恢复第二套 Dart ACP transport；远程 ACP 若立项，仍须沿 Rust 单一权威实现。

## 6. 下一阶段路线：按验收门槛推进

时间段仅为单个维护者安排顺序的示例，不是已估工承诺。建议先做一个约四到六周的收敛周期，并用真实任务结果决定下一周期。

| 批次 | 工作 | 验收门槛 | 先后依赖 |
|---|---|---|---|
| A：能力校准 | 一张当前能力清单；纠正 Coverage/fork/usage 等承诺；统一终端术语；清理无功能分组 | 每个对外“可用”项能对应生产路径；不支持项无法误导创建不可执行会话 | 先做，不依赖大重构 |
| B：主流程精简 | 整合诊断、会话菜单、设置层级；当前项目/Agent 默认值；统一错误恢复；清理旧组件 | 用同一组新建、恢复、取消、授权、结果打开、归档任务证明步骤清楚且无能力丢失 | 在 A 的能力边界上设计 |
| C：真实兼容与可靠性 | 选择一到两个主力 Agent 做完整真实矩阵，其余明确支持等级；补关键生产投影/失败路径 | 创建→发送→权限→停止→恢复→关闭→进程恢复均有真实记录；失败能回到可操作状态 | 不以 Fake 单测替代 |
| D：可选层收益验证 | 对模板、AI reviewer、AI summary、本地终端、worktree 收集最小使用证据 | 能说明解决了什么重复任务、额外延迟/调用、是否愿意持续使用 | 没有证据就保持高级/冻结，不扩大 |
| E：下一方向决策 | 选择继续桌面会话、加强诊断，或独立试验某个新需求 | 一次只启动一个新产品模型，有明确用户与成功/退出标准 | A–D 后决定 |

主力 Agent 由实际使用决定，不因为已内置四个 detector 就平均投入四倍完整支持承诺。扩展可保留，支持等级要诚实。正式发布前再完成现有 macOS 签名、公证及真实桌面验收；发布脚本和 CI 配置本身不证明当前已经发布成功。

## 7. 用什么判断精简是否有效

当前已有 `SessionLoadMetrics`（`chat_controller.dart:40`），但这是内部技术指标。本轮没有找到产品级激活、留存或功能采用率数据。可以先用本地诊断记录、任务日记和五位目标用户的小规模试用，不必先建设遥测平台；如果要上传数据，另行定义范围和用户选择。

| 指标 | 定义与采集方式 | 用途 |
|---|---|---|
| 首个成功会话 | 从首次打开到真实 Agent 完成首轮；分别记录安装、配置、认证、模型响应耗时/失败 | 找到真正的上手阻塞，而非只缩短弹窗 |
| 实际任务成功 | 每次试用预先写明目标；结束后记录完成/未完成及原因 | 核心结果，不用消息数量替代 |
| 恢复成功与可见耗时 | 区分同窗口切换、缓存命中、无缓存 load；记录失败回滚 | 避免用 warm cache 掩盖首次恢复问题 |
| 客户端响应性 | 加载中输入/取消/切换可用，长会话未失去响应 | 区分 Agent 读取慢与客户端卡顿 |
| 权限效率 | 人工决策时间、重复授权、审查成功/未知、额外耗时和调用量 | 判断 trust/reviewer 是否值得保留 |
| 可选功能复用 | 用户是否在不同真实任务中再次主动使用模板/终端/worktree/AI总结 | 一次尝鲜不作为扩张依据 |
| 维护成本 | 每次缺陷涉及哪些模块与 Agent 组合，回归时间、复发次数 | 衡量简化是否减少变更负担 |

建议首轮试用任务：首次连接并改一个小问题；同时运行两个项目会话；中途停止并发送新指令；处理文件/命令授权；打开结果文件；恢复长历史；退出/重启 Agent 后继续。至少覆盖一个不支持某能力的 Agent/fixture，验证降级表述。具体耗时门槛应先测基线再定，不把历史 2.2 秒缓存成绩当当前承诺。

AI summary 的退出标准建议：若目标用户读完主回答后几乎不主动查看总结，或总结重复内容、额外等待明显，就改按需或删除自动逐回合生成。Reviewer 的退出标准建议：若大部分请求仍需人工，且审查增加等待/调用，就回到人工加简单稳定规则。模板的扩张标准建议：用户跨任务反复手工改同一组合，才增加对应预设能力。
